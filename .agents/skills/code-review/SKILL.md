# コードとテストのレビュー手順

テストケースの変更時や一定規模以上のコード変更時に、Claude に差分を検査させます。実装上の不備や設計不変条件からの逸脱、不適切なテスト修正をコミット前に検出することが目的です。

## 発火条件と実行タイミング

次のいずれかに該当する場合は、このスキルに従ってレビューを実施します。

* テストファイルの追加または修正
* 約 50 行以上の本番コード変更
* 複数ファイルにまたがる本番コード変更
* 重要境界に関わる本番コード変更

重要境界には、`GlitchEngine` のセッション寿命と非同期 WIT 呼び出し、3 段フレームパイプラインとバッファプール、`MediaPipe` CPU グラフとマスク合成、`Mp4VideoRecorder` と `MediaStoreHelper` の資源管理、および ProGuard とベースラインプロファイルが含まれます。実行タイミングはローカルでのユニットテストおよびビルドがすべて成功した直後とします。コミットおよび PR の作成は、このレビューと指摘事項の修正を完了させてから行います。

## ステップ 1 レビューの実行手段の選択と起動

状況に応じて、次の 3 つの手段のいずれかを選択してレビューを実行します。

* ローカルの `claude` コマンド
* サブエージェントの起動
* `swarm` ワーカーの起動

ローカルの `claude` コマンドを使う場合は、認証済みの `/Users/chikoski/.local/bin/claude` を利用します。サンドボックス外のバイナリとネットワーク通信を使用するため、`run_command` で `BypassSandbox: true` を指定して実行してください。`-p` と `--permission-mode plan` などを指定して非対話かつ読み取り専用で実行し、プロンプトにレビュー依頼内容を渡します。

サブエージェントを使う場合は、`invoke_subagent` ツールで `research` などの読み取り専用サブエージェントを起動し、プロンプトに検査対象と観点を渡します。

`swarm` ワーカーを使う場合は、`swarm` ツールの `add` アクションを呼び出して起動します。`name` には `code-reviewer`、`model` には `claude-opus-5-5-high`、`workspace` には `inherit` を指定します。`claude-opus-5-5-high` のクォータが枯渇している場合は、`claude-sonnet-5-5-high` を指定します。実行中にクォータ上限へ達した場合も、同じ代替モデルへ切り替えます。

## ステップ 2 レビュー指示と検査観点

レビュー担当者への依頼内容には、変更の目的、関連する Issue や ADR の番号、`git status` と `git diff` を用いてワークツリーの差分を確認する指示を含めます。あわせて、[CLAUDE.md](../../../CLAUDE.md) と [AGENTS.md](../../../AGENTS.md) の不変条件を参照するよう伝えます。レビュー担当者は読み取り専用で検査のみを行い、ファイルを直接編集せずに指摘事項を出力または `@coordinator` 宛てにボードへ投稿させます。

レビュー担当者には次の 5 つの観点で差分を検査させます。

* 不変条件の遵守
* 並行処理と資源寿命の安全性
* 録画と保存の異常系処理
* Android ビルドと R8 の整合性
* テストの妥当性と網羅性

不変条件の遵守では、`GlitchEngine` の `Mutex` 直列化と `ColorType.RGB` エンコード、および `CpuSelfieSegmenterGraph.kt` の `com.google.mediapipe.tasks.core` パッケージ配置が保たれているかを確認させます。並行処理と資源寿命の安全性では、`ImageProxy` の確実なクローズ、`FrameBufferPool` の取得と返却の対、および `PreviewRenderer` と `GlitchEngine` の破棄時の競合防止を点検させます。

録画と保存の異常系処理では、`Mp4VideoRecorder` の 0 フレーム終了時と EOS タイムアウト時の振る舞い、および `MediaStoreHelper` の失敗時の一時ファイルと保留レコード削除を確認させます。Android ビルドと R8 の整合性では、Gradle 設定、ProGuard ルール、およびベースラインプロファイルの記述が最新のパッケージ名やクラス構成と一致しているかを点検させます。テストの妥当性と網羅性では、テストのスキップや無効化、アサーションの緩和が行われていないかを確認させ、境界値や異常系のテストケースが十分かを評価させます。

## ステップ 3 修正とエスカレーション

選択した実行手段の出力、サブエージェントからの返答、または `swarm_wait` と `read_board` でレビュー報告を受け取ります。指摘された実装上のバグやエッジケースのテスト不足は、メインエージェントが自律的に修正します。修正後はローカルのユニットテストとビルドを再度実行し、すべて通ったことを確認した上で必要に応じて再確認を依頼します。`swarm` ワーカーの場合は `post_message` で `@code-reviewer` に依頼します。サブエージェントの場合は `send_message` で、ローカルコマンドの場合は修正後の差分を添えた再実行で依頼します。再確認のやり取りは最大 2 往復までとします。

既存テストケースの期待値を変更する必要があり、かつその変更が仕様変更やユーザー体験の大きな変更を伴う場合は、自律的に修正を確定してはなりません。また、設計上のトレードオフ判断が必要な指摘を受けた場合も同様です。該当する論点と変更影響を整理し、ユーザーへエスカレーションして確認を求めます。

## ステップ 4 後処理

すべての指摘への対応とローカルテストの再確認が完了したら後処理を行います。`swarm` ワーカーを起動した場合は、`swarm` ツールの `kill` アクションで `code-reviewer` を終了します。その後、変更のコミットと PR 作成へ進みます。
